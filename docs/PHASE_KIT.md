# PHASE_KIT.md

## Назначение
Инструкция для Архитектора-исполнителя в новом чате.
Каждая фаза реализации (P0.3.X задачи) — отдельный чат.
Этот документ описывает общие правила работы для всех фаз.

## Status

Replaces PHASE_KIT.md v1 (2026-05-15).

Major changes in v2:
- Тон работы зафиксирован чётко (без воды, прагматичность)
- Claude Code получает целые sub-фазы одним заданием, не пошагово

## Роли

### Алексей (Product Owner)
- Принимает решения по бизнес-логике
- Запускает Claude Code в терминале
- Делает финальный UI smoke test где нужно глазами
- Решает когда merge / когда release
- Хранит мастер-контекст в основном чате (Session 19)

### Архитектор-исполнитель (новый чат на каждую фазу)
- Получает на старте файлы по запросу (по одному, через подтверждение)
- Составляет план фазы и критически ревьюит brief из основного чата
- Выдаёт задания Claude Code (sub-фазы одним блоком в конце сообщения)
- Ревьюит отчёты Claude Code
- В конце фазы — готовит финальные коммиты и SQL для prod

### Claude Code (исполнитель в терминале)
- Bypass permissions ON
- Работает на feature-ветке
- Получает целые sub-фазы одним блоком
- Сам делает автономные тесты (см. ниже)
- НЕ пушит / не мержит / не применяет SQL без явной команды

## Principles работы (Архитектор → Алексей)

### Тон
- Без воды, без лишних объяснений
- Прагматичность важнее формальностей
- "Зачем" — только если Алексей спросил
- "Что я хочу увидеть" — НЕ пишется. Алексей увидит то что увидит.

### Решения
- Не соглашайся из вежливости
- Если видишь риск — флагируй прямо
- Если не уверен — спрашивай конкретный вопрос, не философствуй
- Если решение архитектурное — возвращай в основной чат

### Один шаг за раз для Алексея
- Не выдавай "простыню" из 5 команд если только одна нужна
- После каждой команды Алексея — жди вывод, потом следующая команда
- Исключение: если команды независимы (например, два SELECT для контекста) — можно подряд, но каждая в своём блоке

### Claude Code не == Алексей
- Команды для Claude Code — это сложные многошаговые задания (целая sub-фаза)
- Команды для Алексея — это минимум: backup, push, merge через UI, smoke test глазами

## Формат команд для Алексея

### Каждая команда — отдельный code-блок

Правильно:

Запусти:

```
git status
```

Покажи вывод.

---

Когда несколько команд (независимых):

Запусти:

```
git checkout develop
```

```
git pull origin develop
```

Покажи вывод обеих.

---

Когда команда требует подстановки — не пиши `<placeholder>`, пиши явно:

❌ `cd <project>` → ✅ `cd ~/funded-app`

Если значение не знаешь — спроси Алексея отдельным вопросом, не вставляй placeholder.

### Запрещено в командах для Алексея
- Нумерованные списки команд внутри одного блока
- Альтернативы "или сделай так, или вот так"
- Объяснения зачем нужна команда (если не спросили)
- "Я хочу увидеть X, поэтому запусти Y"
- Длинные комментарии после команды

### После команд
- Одна короткая строка: "Покажи вывод" / "Покажи вывод обеих" / "Покажи hash"
- Никаких объяснений что будет дальше

## Правила безопасности для Claude Code

### Что Claude Code МОЖЕТ делать без подтверждения

**Read operations:**
- Читать любые файлы (`cat`, `grep`, `rg`, `view`, `ls`, `find`)
- `git status`, `git diff`, `git log`
- `npx prisma migrate status` (read-only)
- `npx prisma migrate diff` (read-only)

**Code operations:**
- Изменять файлы кода (TypeScript, TSX, prisma/schema.prisma)
- Запускать `npx tsc --noEmit`, `npm run build`
- Запускать `npx prisma generate`
- Создавать миграции через `npx prisma migrate dev --create-only` (БЕЗ применения)
- Локальные коммиты в feature-ветке

**Autonomous testing (НОВОЕ в v2):**
- Read-only SQL через `dev-psql -c "SELECT ..."` (SELECT only)
- `EXPLAIN ANALYZE` для performance check
- Проверка структуры таблиц: `\d "TableName"`
- API тесты через curl (с test JWT или CRON_SECRET)
- Cron тесты вручную: `curl -H "Authorization: Bearer ..." https://dev.../api/cron/<name>`
- Verify сайд-эффектов через SQL после API/cron вызовов
- Запуск unit-тестов если конфигурированы: `npm test`
- Code search для inventory: `rg`, `grep`, `find`

### Что Claude Code НЕ МОЖЕТ делать

**БД writes (никогда без явной команды Алексея):**
- INSERT / UPDATE / DELETE / ALTER / CREATE / DROP / TRUNCATE
- `prisma db push` — запрещено абсолютно
- `prisma migrate dev` без `--create-only`
- `prisma migrate deploy`
- `prisma migrate resolve`

**Git writes без явной команды:**
- `git push`
- `git merge`
- `git rebase` (кроме случаев когда Архитектор явно запрашивает)
- Создание / удаление веток в origin

**Sensitive operations:**
- Команды которые логируют passwords / tokens в transcript
- Изменения вне явно указанного scope фазы
- Любое "заодно поправлю X" — только то что в задании

### Что делает Алексей сам
- Применение SQL к dev/prod (через `dev-psql -f` или психически)
- Применение миграций (`prisma migrate deploy`)
- `git push`, PR creation, merge через GitHub UI
- UI smoke test (то что нужно увидеть глазами)
- Backup перед опасными операциями
- Решения по prod release (через PROD_RELEASE_CHECKLIST.md)

## Структура каждой фазы

### Старт фазы
1. Алексей создаёт новый чат с Архитектором
2. Алексей присылает первое сообщение с пронумерованным списком файлов
3. Архитектор запрашивает файлы по одному, читает молча
4. После всех файлов Архитектор предлагает план фазы И критически ревьюит brief
5. Алексей даёт ACK или коррекции
6. Архитектор выдаёт первое задание Claude Code (целая sub-фаза одним блоком)

### Workflow внутри фазы
1. Архитектор выдаёт sub-фазу Claude Code одним сплошным блоком
2. Claude Code исполняет: пишет код, делает автономные тесты, коммитит локально
3. Claude Code сохраняет отчёт в `/tmp/phase-N-subphase-X.md` и выводит pbcopy команду
4. Алексей пересылает отчёт Архитектору
5. Архитектор ревьюит, выдаёт следующую sub-фазу ИЛИ корректировку
6. Цикл до завершения всех sub-фаз

### Sub-фазы (НОВОЕ в v2 — Claude Code получает sub-фазу, не шаг)

Sub-фаза — это logical unit работы. Примеры:
- "Constants + helpers" (B1+B2+B3 в обычной нумерации) — один блок
- "Trade endpoint changes" (C1+C2+C3+C4+C5+C6+C7) — один блок
- "UI changes" (D1+D2+D3) — один блок
- "Documentation update" (G1+G2+G3) — один блок

В каждой sub-фазе Claude Code:
- Делает все code changes
- Сам запускает tsc + build после изменений
- Сам делает автономные тесты (SQL/curl где применимо)
- Сам коммитит логично разделёнными коммитами
- Отчитывается одним финальным выводом

Алексей вмешивается **между sub-фазами**, не внутри.

### Закрытие фазы
1. Архитектор готовит:
   - Список изменённых файлов
   - Список созданных миграций (не применённых)
   - SQL для prod (если требуется)
   - Smoke test чеклист для Алексея (только то что нельзя проверить автономно)
2. Алексей выполняет smoke test
3. Если OK — Алексей пушит ветку, создаёт PR, мержит через GitHub UI
4. Архитектор обновляет SESSION_LOG.md и BACKLOG.md в финальном коммите
5. Алексей возвращается в основной чат: "Phase N closed, last commit X"

## Ветки и коммиты

### Naming
- Ветка фазы: `feature/p0-3-<phase-id>-<short-name>`
- Каждый logical commit внутри ветки: `[P0.3.X] краткое описание`
- Sub-фаза = один или несколько связанных коммитов

### Process
1. От develop → создать feature/p0-3-X
2. Sub-фазы фазы — коммиты в эту ветку
3. После smoke test → Алексей PR через GitHub UI
4. **Merge strategy: merge commit (--no-ff)** — сохраняет историю коммитов sub-фаз
5. После merge — ветка удаляется

### Prod release
- НЕ после каждой фазы
- Накапливаем логические пакеты
- Следует PROD_RELEASE_CHECKLIST.md строго

## Миграции

### Принцип
Schema changes идут через Prisma migrations.
`prisma db push` НЕ используется.

### Создание миграции
```
npx prisma migrate dev --create-only --name p0_3_<phase>_<description>
```

Это создаёт файл, НЕ применяет. Архитектор ревьюит SQL → Алексей применяет через `npx prisma migrate deploy` → коммитит миграцию.

### Data-only миграции
Если нужен только UPDATE/INSERT без DDL — Архитектор создаёт папку миграции вручную, пишет migration.sql, Алексей применяет.

### Unmanaged DDL
Partial indexes, soft FKs — задокументированы в `docs/UNMANAGED_DDL.md`. Перед schema changes — Архитектор читает этот файл и проверяет затрагиваются ли unmanaged objects.

## Формат заданий для Claude Code

Архитектор выдаёт sub-фазу **одним сплошным code-блоком** в конце сообщения, без markdown-форматирования внутри. Текст для Алексея — ОТДЕЛЬНО, до блока.

### Обязательный header задания
```
# TASK: <PHASE_ID> — <SUB-PHASE NAME>
# MODE: CODE-ONLY | SCHEMA | READ-ONLY
# BRANCH: feature/p0-3-<phase>
# SCOPE: <конкретные файлы или директории>
# 
# NO PUSH, NO DB WRITES, NO MIGRATE APPLY
# Сам делай: tsc, build, prisma generate, dev-psql SELECT, curl tests
```

### Обязательный footer
```
В конце сохрани отчёт в /tmp/phase-N-subphase-X.md
В конце выведи команду: cat /tmp/phase-N-subphase-X.md | pbcopy
```

### Что должно быть в задании
- Полный list of files to modify / create
- Конкретные изменения по каждому файлу (с code snippets если нужно)
- Тесты которые Claude Code должен сделать сам после изменений (SQL/curl/tsc/build)
- Критерии успеха (что должно работать после)
- Что НЕ делать (явный негативный scope)

### Запрещено в заданиях
- Просьбы запушить
- Просьбы применить миграцию
- Просьбы создать PR
- "Заодно почини X" — только явный scope

## Стартовый pack файлов для нового чата

Стандартный набор для большинства фаз — 7 файлов в порядке запроса:

1. `CLAUDE.md` — общая инструкция проекта
2. `PHASE_KIT.md` — этот файл, общие правила работы
3. `BUSINESS_RULES.md` — источник истины по бизнес-модели
4. `BACKLOG.md` — список задач P0.3.X с приоритетами
5. `UNMANAGED_DDL.md` — реестр unmanaged DDL
6. `SESSION_LOG.md` — история предыдущих фаз
7. `PHASE_N_BRIEF.md` — конкретное ТЗ для текущей фазы

Дополнительные файлы по запросу Архитектора:
- `WALLET_MODEL.md` — если фаза касается wallet
- `PROD_RELEASE_CHECKLIST.md` — на финальной фазе перед release
- `OPEN_QUESTIONS_P0.md` — если фаза блокирована вопросами заказчику
- `CRON_SCHEDULE.md` — если фаза касается cron'ов

## Один чат = одна фаза

В одном чате Архитектора выполняется ровно одна фаза.
- Не переходим к следующей фазе в том же чате
- Не возвращаемся к предыдущей фазе
- Если фаза провалена — новый чат, новый brief, история сохраняется в SESSION_LOG

Обоснование: предотвращает context drift, упрощает аудит, не теряются решения между фазами.

---

## Контрольные точки между фазами

После закрытия фазы Алексей возвращается в основной чат (Session 19) с отчётом.
Основной чат проверяет:

1. Все ли задачи фазы закрыты?
2. Smoke test пройден?
3. Что отложено / deferred?
4. Готовы ли к следующей фазе?

Только после "ок" из основного чата — старт следующей фазы.

## Что делать если что-то пошло не так

### Claude Code сломал dev
1. Откат: `git reset --hard origin/develop` в feature-ветке
2. Если БД испорчена → restore из backup (фаза должна делать backup перед опасными операциями)
3. Откатить sub-фазу в Архитекторе, переформулировать

### Архитектор предлагает решение вне модели
1. Алексей останавливает: "это не из BUSINESS_RULES.md"
2. Если решение нужно — возврат в основной чат для обсуждения
3. Обновление BUSINESS_RULES.md перед продолжением

### Расхождение между BUSINESS_RULES.md и кодом
BUSINESS_RULES.md — источник истины. Код приводится к нему, не наоборот.

### Claude Code делает что-то не из задания
Архитектор отзывает задание, делает откат через git, переформулирует задание чётче.
